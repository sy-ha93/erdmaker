로그인·DB·서버 없이 가고 협업은 Git으로 하기로 하면서 계획에서 빠진 것이다. 근거는 기획 3.5~3.7절과 5.2절이다.

- 모델 원본을 브라우저 안(SQLite WASM, OPFS)에 두는 것

- `docker compose` 자체 호스팅, 클라우드 호스팅
- 실시간 공동 편집, 동기화 서버, 공유 링크와 역할 관리
- 앱 안의 Git 조작(브랜치, 커밋, 푸시, PR 생성)과 GitHub App 인증

Git에서 읽기만 하는 기능(기준 버전과 비교)은 F14에 있다. 병합 화면과 PR 자동 검사는 2단계다.

### 확정된 것 (2026-11-26)

- **실행 방식** (이전 D2, 2026-11-27에 `serve`에서 PWA로 변경): 브라우저에 설치하는 웹앱이다. Chrome이나 Edge에서 주소를 열어 설치하고 모델 폴더를 한 번 고르면, 화면이 그 폴더를 직접 읽고 쓴다(File System Access API). 파일이 밖에서 바뀌면(MCP, 코딩 에이전트, `git pull`) 화면이 감지해 다시 읽는다. 로그인, DB, 서버가 없고 Node 설치도 필요 없다. 편집은 Chrome·Edge에서만 되고, 폴더 접근·변경 감지·Git 읽기가 막히면 같은 화면을 `npx erdmaker serve`로 낸다.
- **협업**: 사람마다 브랜치에서 작업하고 GitHub/GitLab의 PR로 합친다. 앱은 Git을 조작하지 않는다. 브랜치, 커밋, 푸시, PR은 사용자의 Git 클라이언트나 코딩 에이전트로 한다.
- **논리와 물리**: 1:1로 한 모델에 함께 둔다.
- **묶는 단위** (2026-11-27): 프로젝트(Git 저장소, 모델 여러 개) → 모델(스키마 여러 개) → 주제영역(묶음 한 단계). 여러 모델 열기는 MVP에 넣는다.
- **저장소** (이전 D1, 2026-11-27): github.com/sy-ha93/erdmaker, 공개, Apache-2.0. 제품 이름이 바뀌면 저장소 이름도 바꾼다.

## 4. 기능 상세

각 기능은 yyy-workflow 실행 한 번이다. "범위"와 "수용 기준"을 Phase 0의 요구사항으로 그대로 넘긴다. 공통 사항:

- 코어·CLI·MCP 기능의 관문은 단위 테스트다. E2E와 디자인 리뷰는 건너뛴다.
- 화면 기능은 조작 대상에 `data-testid`를 붙이고 명령 API를 `window.__erd`로 노출한다. 캔버스 드래그는 E2E에서 불안정하므로 결과는 명령 API와 파일 내용으로 확인한다.
- 초기 기능은 기존 코드가 없다. 분석 단계의 필수 참고 파일로 `docs/format-v0.md`, `format/v0/schema/`, `format/v0/examples/shop/`, `packages/core`를 지정한다.

### F01 `repo-scaffold` (1일)

- **상태**: 완료 (2026-11-27, PR #3). 스펙·분석·계획은 `docs/specs`, `docs/analysis`, `docs/plans`의 `repo-scaffold.md`.
- **범위**: pnpm 워크스페이스. 패키지 `core`, `cli`, `mcp`, `web`. TypeScript, Vitest, ESLint, Prettier, GitHub Actions(빌드·테스트·린트·`validate:format`). Apache-2.0 `LICENSE`.
- **제외**: 기능 코드.
- **수용 기준**: `pnpm build`, `pnpm test`, `pnpm lint`가 빈 패키지에서 통과한다. CI가 같은 명령을 돌린다. 기존 `npm run validate:format`이 계속 통과한다.

### F02 `core-model-io` (3일)

- **상태**: 완료 (2026-11-28, PR #5). 스펙·분석·계획·결정 기록은 `docs/specs`, `docs/analysis`, `docs/plans`, `docs/decisions`의 `core-model-io.md`.
- **범위**: 형식 v0 모델 디렉터리를 메모리 모델로 읽고 다시 쓴다. 옛 검사 도구의 스키마 검사와 파일 간 규칙 12개를 코어로 옮긴다. 프로젝트 폴더에서 모델 폴더를 찾는다(형식 문서의 "프로젝트, 모델, 주제영역"). CLI `erdmaker validate <dir>`.
- **제외**: 편집 명령, 형식 마이그레이션.
- **수용 기준**:
  - `format/v0/examples/shop`을 읽고 쓰면 파일이 바이트 단위로 같다.
  - `erdmaker validate <프로젝트 폴더>`가 그 안의 모델을 모두 찾아 검증하고, 모델 `id`가 겹치면 오류다.
  - 깨진 배치 JSON을 만나면 죽지 않고 오류로 보고한다(F01에서 넘긴 옛 검사 도구의 버그).
  - 검증 규칙마다 위반 예제가 하나 이상 있고, 오류 메시지에 파일과 위치가 나온다.
  - YAML 1.2 core 스키마만 쓴다(`NO`가 문자열로 남는다). 앵커·별칭·태그는 오류다.
  - 코어는 브라우저와 Node 양쪽에서 돈다(파일 접근은 어댑터로 분리).

### F03 `core-commands` (3일)

- **상태**: 완료 (2026-11-28, PR #6). 스펙·분석·계획·결정 기록은 `docs/specs`, `docs/analysis`, `docs/plans`, `docs/decisions`의 `core-commands.md`.
- **범위**: 명령 API. 엔터티·속성·키(PK, AK, IE) 생성·수정·삭제·순서 변경, 이름 변경, 주제영역 편집, `scope` 변경. 실행 취소·다시 실행. 이름에서 ID 생성(고정, 충돌 시 접미사). 명령마다 검증을 돌려 깨진 모델을 만들지 않는다.
- **제외**: 관계(F04), 사전(F05).
- **수용 기준**:
  - 모든 명령이 직렬화 가능한 객체이고, UI·MCP·CLI가 같은 진입점을 쓴다.
  - 명령 실행 → 실행 취소 → 저장하면 원래 파일과 같다.
  - 이름을 바꿔도 ID는 바뀌지 않는다.
  - 명령 하나가 바꾼 파일만 다시 쓴다.

### F04 `core-relationships` (4일)

- **범위**: 식별·비식별·다대다 관계 생성·수정·삭제. 부모 키의 FK 자동 이주(`migratedFrom`), 부모 키 변경의 전파, 식별 ↔ 비식별 전환, 롤네임, 자기 참조, 단일화(같은 속성이 두 경로로 이주), 카디널리티, 참조 무결성 동작 값 저장. 서브타입 묶음(표기에 필요한 데이터까지). 다대다의 `resolvedBy`.
- **제외**: 서브타입의 물리 변환, N항 관계, RI 트리거 생성(모두 2단계).
- **수용 기준**:
  - ERwin 개요 문서의 이주 규칙을 테스트 케이스로 옮겨 통과한다(식별이면 자식 PK에 포함, 비식별이면 비키 속성, 자기 참조는 롤네임 필수).
  - 부모 PK에 속성을 추가하면 자식과 손자까지 이주하고, 실행 취소 한 번으로 되돌아간다.
  - 관계를 지우면 이주된 속성이 사라진다. 롤네임 속성의 처리 방식은 스펙에서 정한다.
  - 예제 모델의 관계 11개와 서브타입 1개를 명령만으로 다시 만들면 같은 파일이 나온다.

### F05 `core-dictionary` (3일)

- **범위**: 사전 파일(단어·용어·도메인) 읽기와 편집 명령. 한글 용어를 단어로 분해해 물리명 생성(고객번호 → `CUST_NO`). 도메인을 속성에 적용하고 DBMS별 물리 타입으로 풀기. 준수 검사(사전에 없는 단어, 약어 불일치, 도메인 불일치)와 준수율.
- **제외**: 엑셀 가져오기(선 아래), 동의어·금칙어 처리 규칙의 고도화.
- **수용 기준**:
  - 예제 사전(단어 5, 용어 4, 도메인 8)으로 예제 모델의 물리명이 재현된다.
  - 분해가 여러 가지로 되는 용어는 후보를 모두 돌려주고, 임의로 고르지 않는다.
  - CLI `erdmaker check-naming <dir>`가 위반 목록과 준수율을 낸다.

### F06 `ddl-export` (3일)

- **범위**: 물리 모델에서 MySQL·PostgreSQL DDL 생성. 테이블, 컬럼, 타입, NULL 여부, 기본값, PK·AK·인덱스, FK와 참조 동작, 주석. `scope: logical` 객체는 제외. CLI `erdmaker export ddl --dialect`.
- **제외**: ALTER·마이그레이션 생성, 트리거, 뷰, 다른 DBMS.
- **수용 기준**:
  - 같은 모델에서는 항상 같은 DDL이 나온다(바이트 단위).
  - 예제 모델의 DDL이 실제 MySQL과 PostgreSQL에서 오류 없이 실행된다(CI에서 컨테이너 또는 PGlite).
  - 방언은 인터페이스로 분리돼 세 번째 방언을 코어 수정 없이 추가할 수 있다.

### F07 `ddl-import` (5일)

- **범위**: MySQL·PostgreSQL DDL을 모델로 변환. 테이블·컬럼·키·FK·인덱스·주석. 주석은 논리명 후보로 쓴다. FK는 관계와 `migratedFrom`으로 바꾼다. 격자 초기 배치. 주제영역 초안 자동 생성: 스키마별로 나누고, 그 안에서 테이블 이름 접두어로 묶고, 작은 묶음은 "기타"로 모은다. CLI `erdmaker import ddl`.
- **제외**: FK 제약이 없는 스키마의 관계 추정(2단계), 뷰·트리거·프로시저.
- **수용 기준**:
  - 363개 테이블 스키마를 가져와 `validate`를 통과한다(D3에 따라 대체 스키마 포함).
  - 가져오기 → DDL 내보내기 → 다시 가져오기의 결과가 같은 모델이다.
  - 해석하지 못한 문장은 버리지 않고 위치와 함께 보고한다.
  - 스키마가 둘 이상인 DDL을 가져오면 `schemas`가 채워지고, 이름이 겹치는 테이블의 ID에 스키마 이름이 붙는다.
  - 모든 테이블이 주제영역 하나 이상에 들어가고, 영역 초안을 끄는 옵션이 있다.

### F08 `mcp-server` (3일)

- **범위**: stdio MCP 서버. 읽기(`list_entities`, `get_entity`, `search_model`, `get_subject_area`, `lookup_term`), 편집(`create_entity`, `add_attribute`, `create_relationship`, `rename`, `apply_changeset`), 검증(`validate_model`, `check_naming`), 생성(`generate_ddl`). 편집 도구는 `.erdmaker/changesets/`에 변경안 파일을 만들고, `apply_changeset`이나 자동 적용 설정으로 반영한다.
- **제외**: HTTP 전송, DB 도구(`introspect_database` 등), 버전 도구(`commit`, `open_pull_request` 등), `lint`, `generate_migration`.
- **수용 기준**:
  - Claude Code에 연결해 "예제 모델에 배송 엔터티를 추가하고 주문과 연결"을 시키면 변경안이 생기고, 적용 뒤 `validate_model`이 통과한다(완료 기준의 MCP 부분).
  - 도구는 코어 명령 API만 호출한다. 모델 로직을 다시 구현하지 않는다.
  - 잘못된 입력은 어느 규칙을 어겼는지 담은 오류로 돌려준다.

### F09 `web-viewer` (7일)

- **범위**: PWA 틀(매니페스트, 서비스 워커, 설치 가능, 오프라인에서 열림). 브라우저용 파일 어댑터: 모델 폴더 열기(File System Access API), 다시 열 때 폴더 기억, 변경 감지(FileSystemObserver). 예제 모델 열기: 예제를 브라우저 내부 저장소(OPFS)에 복사해 같은 어댑터로 연다(체험용이자 E2E용). 폴더 접근을 지원하지 않는 브라우저에는 안내 화면. 화면 틀 4구역(기획 6장). 프로젝트 폴더를 열면 그 안의 모델을 모두 찾아 상단 바에서 전환한다. 왼쪽 패널에 묶음 → 주제영역 트리와 스키마 필터. 캔버스 위에 열어 둔 주제영역 탭. 엔터티 목록과 통합 검색. 읽기 전용 캔버스: IE 표기, 식별 실선·비식별 점선, 서브타입 기호, 논리명/물리명 전환, 표시 수준(엔터티·키·속성), 주제영역 전환, 미니맵, 화면 맞춤. 오른쪽 패널에 선택한 엔터티의 속성 표. URL로 엔터티·주제영역 지정.
- **제외**: 편집, 다크 테마, IDEF1X 표기, 호스팅 배포(릴리스에서 한다).
- **첫날에 할 일**: 폴더 열기, 변경 감지, `.git`에서 `main`의 파일 읽기(isomorphic-git)를 먼저 붙여 본다. 하나라도 안 되면 Node 어댑터에 화면을 붙여 `serve`로 바꾸고 이 절과 기획 3.7절을 고친다.
- **수용 기준**:
  - 예제 모델이 주제영역 3개와 배치 2개 그대로 열린다.
  - 모델이 둘인 프로젝트 폴더를 열면 두 모델을 오갈 수 있고, 마지막에 본 모델과 탭을 기억한다.
  - 주제영역이 묶음 아래에 `order` 순서로 보이고, 영역을 누르면 탭으로 열린다.
  - 스키마 필터를 고르면 그 스키마의 엔터티만 목록과 캔버스에 남는다.
  - Chrome에서 설치할 수 있고, 설치한 뒤 네트워크 없이 열린다.
  - 폴더를 고르면 모델이 열리고, 다시 열 때 폴더를 새로 고르지 않아도 된다(권한 확인은 뜰 수 있다).
  - 파일을 밖에서 고치면 새로고침 없이 반영된다.
  - 폴더 선택 창은 E2E에서 누를 수 없으므로, E2E는 "예제 모델 열기"로 들어가 같은 어댑터를 거친다.
  - 363개 테이블 모델에서 이동·확대가 P4에서 정한 예산 안이다.
  - `#…/table/<id>` 주소로 열면 그 엔터티가 선택된 상태다.

### F10 `canvas-edit-entity` (4일)

- **범위**: 엔터티 생성·삭제·이동(배치 파일 저장), 속성 인라인 편집(이름, 타입, 키, NULL), 오른쪽 패널의 편집 폼, 실행 취소·다시 실행 단축키, 변경 즉시 파일 저장, 주제영역에 엔터티 넣고 빼기.
- **제외**: 관계 편집(F11), 여러 개 선택 일괄 편집, 정렬 안내선.
- **수용 기준**:
  - 엔터티를 만들고 속성 3개를 넣으면 `entities/<id>.yaml`이 생기고 `validate`를 통과한다.
  - 엔터티를 옮기면 배치 파일만 바뀌고 모델 파일은 바뀌지 않는다.
  - 화면의 모든 편집이 코어 명령으로 나간다(`window.__erd`의 명령 기록으로 확인).

### F11 `canvas-edit-relationship` (3일)

- **범위**: 엔터티 사이를 끌어 관계 생성, 종류·카디널리티·롤네임·참조 동작 편집, 관계 삭제, 이주된 속성의 표시(FK 표식, 편집 제한). 검증 경고 패널과 캔버스 위 경고 표시.
- **제외**: 관계선 경로 수동 편집, 서브타입 묶음을 화면에서 만드는 것(표시만).
- **수용 기준**:
  - 관계를 그으면 자식에 FK 속성이 즉시 나타나고, 실행 취소 한 번으로 사라진다.
  - 식별 ↔ 비식별을 바꾸면 선 모양과 자식 PK가 함께 바뀐다.
  - 검증 경고를 누르면 해당 객체로 이동한다.

### F12 `canvas-layout` (2일)

- **범위**: ELK 자동 배치(전체, 주제영역), 주제영역별 배치 저장, 배치가 없는 엔터티의 초기 위치.
- **제외**: 배치 알고리즘 선택 화면, 선 겹침 최소화 튜닝.
- **수용 기준**:
  - 1,000개 테이블 자동 배치가 화면을 멈추지 않는다(작업 스레드에서 실행, 진행 표시).
  - 1,000개 테이블에서 이동·확대·엔터티 끌기가 P4의 예산 안이다.

### F13 `dictionary-ui` (3일)

- **범위**: 왼쪽 패널의 사전 탭(단어·용어·도메인 조회와 편집). 속성 이름에 용어를 입력하면 물리명과 도메인 자동 적용. 준수 위반을 캔버스와 목록에 표시하고 준수율 표시.
- **제외**: 엑셀 가져오기, 사전 병합.
- **수용 기준**:
  - 논리명에 "고객번호"를 넣으면 물리명 `CUST_NO`와 도메인 타입이 채워진다.
  - 사전에 없는 단어가 든 속성에 경고가 붙고, 단어를 추가하면 사라진다.

### F14 `changeset-review` (3일)

- **범위**: 모델 diff(엔터티·속성·관계 단위의 추가·변경·삭제). CLI `erdmaker diff <a> <b>`는 폴더 둘 또는 Git 기준 버전(예: `erdmaker diff main`)을 받는다. 화면에서 기준 버전을 골라 캔버스에 추가·변경·삭제를 색으로 표시한다. 대기 중인 변경안 목록과 수락·거절. Git에서는 읽기만 한다. CLI는 시스템의 `git`으로, 화면은 isomorphic-git으로 `.git` 폴더에서 기준 버전의 파일을 읽는다.
- **제외**: 3-way 병합 화면과 `mergetool` 등록(2단계). Git 조작(브랜치, 커밋, 푸시, PR)은 만들지 않는다.
- **수용 기준**:
  - `erdmaker diff main`이 작업 폴더와 `main`의 차이를 내고, 작업 폴더와 Git 상태를 바꾸지 않는다.
  - 화면에서 기준 버전으로 `main`을 고르면 CLI와 같은 차이가 나온다.
  - Git 저장소가 아닌 폴더에서도 편집기와 폴더 간 diff가 동작한다.
  - MCP가 만든 변경안이 화면에 나타나고, 수락하면 파일에 반영되며 거절하면 변경안 파일만 사라진다.
  - `diff`의 출력이 "엔터티 1개 추가, 컬럼 타입 1건 변경" 수준의 요약과 상세를 함께 낸다.

### F15 `export-docs` (3일)

- **범위**: 엑셀 산출물 4종(테이블 정의서, 컬럼 정의서, 엔터티 정의서, 용어사전), 서식 템플릿 교체. DBML 내보내기와 가져오기(`@dbml/core`). Mermaid erDiagram 내보내기.
- **제외**: 엑셀 가져오기(선 아래), ORM 스키마, 마이그레이션 파일(2단계).
- **수용 기준**:
  - 363개 테이블 모델의 테이블·컬럼 정의서가 생성된다(완료 기준의 엑셀 부분).
  - 템플릿 파일을 바꾸면 코드 수정 없이 서식이 바뀐다.
  - DBML로 내보낸 뒤 다시 가져오면 물리 구조가 같다.

### F16 `export-image-viewer` (3일)

- **범위**: 캔버스를 PNG·SVG·PDF로 내보내기(전체 또는 주제영역). 서버 없이 열리는 단일 파일 HTML 뷰어(검색, 논리/물리 전환, 주제영역 전환).
- **제외**: 뷰어에서의 편집.
- **수용 기준**:
  - 363개 테이블 전체를 SVG로 내보내면 글자가 선택되는 벡터다.
  - HTML 뷰어 파일 하나를 `file://`로 열어 검색과 전환이 된다.

## 6. yyy-workflow로 실행하는 방법

기능 하나를 시작할 때:

1. `main`이 깨끗한지 확인한다. 상태 파일 `docs/.yyy-workflow-state.json`은 하나뿐이라 한 번에 한 기능만 돌린다.
2. `/yyy-workflow`에 이 문서의 해당 기능 절(범위·제외·수용 기준)과 slug를 넘긴다.
3. 설정 질문에는 위 표의 E2E·디자인 리뷰 값을 고른다. 브랜치는 Branch.
4. 병합되면 이 문서의 표에 완료일과 실제 일수를 적는다.

기능이 3일을 넘으면 워크플로의 권장 브랜치 수명(1~2일)보다 길다. 계획 단계에서 Phase가 6개를 넘으면 기능을 둘로 나눈다.
