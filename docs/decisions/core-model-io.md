# F02 `core-model-io` 진행 중 결정 기록

2026-11-27부터 사용자 지시에 따라, 선택이 필요한 곳에서는 묻지 않고 권고안대로 진행한다. 이 문서는 그때마다 무엇을 골랐고 왜 그것이 타당한지를 적는다. 범위는 F02의 구현, 리뷰, 테스트까지이고 `main` 병합은 포함하지 않는다. 마지막에 Codex 리뷰를 한 번 더 돌린다.

각 항목은 선택지, 고른 것, 이유, 타당성(무엇으로 확인했는지 또는 확인하지 못했는지) 순서로 적는다.

## 이 지시 전에 이미 정한 것 (참고)

사용자가 직접 고른 것이라 이유만 한 줄씩 남긴다.

| 결정 | 이유 |
| --- | --- |
| YAML 주석은 다시 쓸 때 보존하지 않는다 | 같은 모델이 항상 같은 바이트로 저장돼 Git diff가 깨끗하다. 설명은 `definition`과 `note`에 적는다 |
| 형식 문서와 옛 검사 도구가 다르면 형식 문서를 따른다 | 형식 문서가 기준이고 옛 도구는 시제품이다 |
| 스펙 리뷰 3회, 계획 리뷰 1회 뒤 남은 지적은 고치고 재리뷰 없이 진행 | 남은 지적이 한두 문장짜리였고, 구현 단계마다 코드 리뷰가 있다 |
| 단계 2의 3회차 리뷰 뒤 경고 2건은 고치고 재리뷰 없이 진행 | 리뷰어가 수정안을 임시 사본에서 이미 확인했다 |

## 결정 기록

아래부터 지시 이후의 결정이다.

### D-00. 진행 방식 (2026-11-28, 사용자 지시)

- **지시**: F02뿐 아니라 F03, F04, F05 등 뒤 기능도 같은 방식으로 순서대로 계속 진행한다.
- **해석**: 다음 기능은 앞 기능이 `main`에 들어가 있어야 시작할 수 있다. 그래서 기능마다 PR을 열고, CI 통과와 마지막 Codex 리뷰를 확인한 뒤 스쿼시 병합하고 다음 기능으로 넘어간다. 병합까지 직접 하는 것은 사용자가 같은 날 확인했다("병합도 직접 해줘").
- **멈추는 경우**: 권고안을 고르는 문제가 아닌 것은 멈춘다. 넘을 수 없는 장애, 접근 권한이 필요한 일(예: F09 전에 필요한 `sudo apt install libasound2t64`), 저장소 밖을 건드리는 파괴적 작업이 그렇다.
- **기록**: 기능마다 `docs/decisions/<기능>.md`를 하나씩 둔다.

### D-01. 단계 3 재리뷰(2회차) FAIL 뒤의 처리 (2026-11-28)

- **상황**: 치명 0건, 경고 4건. 1회차의 지적은 모두 해결됐고 새로 나온 것이다.
- **선택지**: (가) 4건을 고치고 3회차 리뷰 (나) 고치고 리뷰 없이 진행 (다) 그대로 진행
- **고른 것**: (가). 리뷰어가 참고로 적은 2건(절대 경로 검사의 위치, getter 테스트)도 함께 고친다.
- **이유**: 경고 가운데 둘은 실제 결함이다. 깊은 폴더에 링크가 있으면 읽기가 깊이의 세제곱으로 느려지고(400단계에 69초), `model.yaml`의 한 줄 때문에 모델 전체 읽기가 실패한다. 수정이 어댑터의 핵심 경로를 건드려서 한 번 더 확인할 값어치가 있고, 이 단계의 리뷰는 아직 한 번 남아 있다.
- **타당성**: 리뷰어가 두 결함을 실제 입력으로 재현하고 시간을 쟀다. 수정 방향(폴더의 실제 경로를 한 번만 구해 재사용, 존재할 수 없는 경로를 "없음"으로 처리)도 리뷰어가 제시했다. 수정 결과는 아직 확인되지 않았다.

### D-02. `dictionaries`의 절대 경로 검사를 어디에 둘 것인가 (2026-11-28)

- **선택지**: (가) 지금처럼 읽을 때(`loadModel`)만 검사 (나) 스키마 파일에 패턴으로 추가 (다) `validateModel`에서 검사하고 읽을 때는 그 폴더를 건너뛰기만 함
- **고른 것**: (다)
- **이유**: (가)는 메모리에서 편집한 모델이 검증을 통과했다가 다시 읽을 때 실패할 수 있다. 편집 기능(F03)이 바로 이 경로를 쓴다. (나)는 형식 자체를 바꾸는 일이고, 이 기능에서 바꾸는 스키마 파일은 하나뿐이라는 스펙(FR-07)과 어긋난다.
- **타당성**: 리뷰어가 세 안을 비교해 (다)를 가장 단순하고 스펙과 맞는 안으로 권했다. "읽고 검증하면 오류가 한 번만 나온다"는 조건을 수정 지시에 넣었다.

### D-03. 단계 3의 3회차 리뷰 FAIL 뒤: 심볼릭 링크를 따라가지 않기로 함 (2026-11-28)

- **상황**: 리뷰 한도(3회)를 다 썼다. 치명 0건, 경고 4건. 넷 다 Node 어댑터가 심볼릭 링크된 폴더를 "안전하게 따라가려고" 넣은 장치에서 나왔다. 호출 사이에 남는 폴더 기록이 낡은 값을 주고 계속 쌓이며, Linux가 아닌 OS에서는 여전히 깊이의 세제곱으로 느리고, 규칙 하나가 테스트되지 않았다.
- **선택지**: (가) 리뷰어의 권고대로 4건을 고치고 진행 (나) 링크를 따라가는 기능 자체를 뺀다
- **고른 것**: (나). 폴더를 나열할 때 심볼릭 링크는 가리키는 대상과 무관하게 목록에서 뺀다. 연 폴더의 경로나 직접 지정한 파일 경로는 운영체제가 평소처럼 해석한다.
- **이유**:
  - 세 번의 리뷰가 모두 같은 곳에서 새 결함을 찾았다. 장치를 더 얹는 방향은 수렴하지 않았다.
  - 이 제품의 주 실행 환경은 브라우저 앱이고, 브라우저의 폴더 접근은 심볼릭 링크를 보여 주지 않는다. Node에서만 링크를 따라가면 CLI와 앱이 같은 폴더를 다른 모델로 읽게 된다.
  - 링크를 따라가지 않으면 순환이 생길 수 없어 상태, 실제 경로 계산, OS별 분기가 모두 필요 없다.
  - 사전을 여러 모델이 함께 쓰는 방법은 이미 있다(`dictionaries: [../shared]`).
- **잃는 것**: 모델 폴더 안에 링크로 걸어 둔 파일이나 폴더는 읽히지 않는다. 옛 검사 도구는 링크를 따라갔으므로 동작이 달라진다. 형식 문서와 스펙의 알려진 한계에 적는다.
- **타당성**: 리뷰어도 "방문한 실제 경로만 건너뛰는" 단순안은 형제 폴더 링크를 따라가야 한다는 스펙과 맞지 않는다고 봤다. 그 스펙 문장 자체가 리뷰 대응으로 내가 넣은 것이라, 요구를 바꾸는 쪽이 맞다고 판단했다. 브라우저가 심볼릭 링크를 보여 주지 않는다는 점은 내 지식에 따른 것이고 이번에 실행해 확인하지 않았다. F09에서 확인한다. 이 변경은 단계 리뷰를 받지 않으며, 브랜치 전체에 대한 마지막 Codex 리뷰에서 본다.

### D-05. 단계 5 리뷰(1회차) FAIL 뒤의 처리 (2026-11-28)

- **상황**: 치명 0건, 경고 3건. 쓰기 코드는 리뷰어가 따로 만든 생성기로 확인해 문제가 없었다(무작위 모델 6,000개, 까다로운 문자열 7,437건, 짧은 문자열 전수 335,923개). 경고는 스펙이 코드와 어긋난 곳 2건과, 검증은 통과하는데 저장은 거부되는 경우 1건이다.
- **선택지**: (가) 경고만 고치고 재리뷰 (나) 경고와 함께 참고 사항 가운데 중요한 것을 고치고 재리뷰 (다) 고치고 재리뷰 없이 진행
- **고른 것**: (나). 함께 고치는 것은 두 가지다.
  - **간헐적으로 실패하는 시간 테스트**: 전체 테스트 15회 가운데 3회 실패했다. 앞 단계의 테스트이고 단계 5의 결함은 아니지만, CI에서 헛된 실패가 나면 이후 모든 기능의 병합이 흔들린다. 시간 테스트를 다른 테스트와 경쟁하지 않게 따로 돌리고 측정을 견고하게 한다.
  - **`=`와 `<<`를 따옴표로 쓰기**: 지금은 `=` 하나만 든 값이 있으면 PyYAML이 파일 전체를 읽지 못한다. 모델 파일을 스크립트로 읽는 사용자가 있을 것이라 싸게 막는다.
- **이유**: (다)는 시간 테스트의 재구성이 테스트 설정을 건드려서 확인 없이 넘어가기 어렵다. (가)는 간헐 실패를 남긴다.
- **타당성**: 간헐 실패는 리뷰어가 15회 반복으로 잰 것이다. 수정 뒤 20회 연속 실행에서 실패 0건을 목표로 하고, 각 시간 테스트가 제곱으로 느린 코드를 여전히 잡는지도 확인하게 했다. 결과는 아직 나오지 않았다.

### D-06. 검증과 저장의 경계 (2026-11-28)

- **선택지**: 256단계보다 깊은 메모리 데이터와 모양이 잘못된 `Model` 객체를 (가) 검증에서 보고한다 (나) 저장할 때만 거부한다
- **고른 것**: 깊은 데이터는 (가), 잘못된 `Model` 객체는 (나)
- **이유**: 깊은 데이터는 사용자 데이터(`ext`)에서 올 수 있고, 편집 기능(F03)이 "검증 통과 → 저장"을 전제로 하므로 검증에서 알려야 한다. `Model` 객체의 모양은 사용자 데이터가 아니라 호출하는 코드의 문제이고 타입이 막는다. 검증기는 이 경우에 죽지 않는 것까지만 책임진다.
- **타당성**: 리뷰어가 깊은 데이터 쪽을 같은 방식으로 권했다. `Model` 모양 쪽은 리뷰어가 "보고하거나, 보고하지 않는다고 스펙에 명시하라"고 했고 뒤쪽을 골랐다.

### D-07. 단계 5 재리뷰(2회차) FAIL 뒤의 처리 (2026-11-28)

- **상황**: 치명 0건, 경고 2건, 참고 4건. 1회차에서 고친 코드는 리뷰어가 실행해 모두 확인했다(깊이 검사, 256/257 경계, 따옴표 처리 134개 문자열, `pnpm test` 6회 연속 통과와 CPU 부하 중 통과). 경고 2건은 모두 스펙 문장과 JSDoc이 코드보다 좁게 적힌 것이고, 동작을 바꿀 곳은 없다.
- **선택지**: (가) 고치고 3회차 리뷰 (나) 고치고 재리뷰 없이 단계 6A로 진행
- **고른 것**: (나). 참고 4건 가운데 3건(시간 테스트 준비 실행 줄이기, 깊이 테스트가 멈추지 않고 빨리 실패하게 하기, 테스트 비교를 정확하게 하기)도 함께 처리하고, 나머지 1건(Proxy)은 알려진 한계에 적는다.
- **이유**: 남은 것이 문서 문장과 테스트 도우미뿐이라 리뷰 한 번(약 13분)을 더 쓸 값어치가 작다. 브랜치 전체에 대한 마지막 Codex 리뷰가 다시 본다.
- **같은 파일 경로 중복을 검증에서 보고하지 않는 이유**: D-06과 같은 기준이다. `file` 값은 사용자 데이터가 아니라 호출하는 코드가 만든다. 파일에서 읽은 모델에는 생길 수 없다. 그래서 검증은 보고하지 않고 저장이 `TypeError`로 거부하며, 스펙의 예외 목록에 적는다. F03이 새 항목의 파일 경로를 만들 때 이 조건을 지켜야 한다.
- **타당성**: 수정 뒤 빌드, 린트, 형식 검사와 `pnpm test` 5회 연속 통과를 확인한다. 재리뷰는 받지 않는다.

### D-08. 단계 6A에서 구현 중 정한 것 (2026-11-28)

스펙과 계획이 정하지 않아 구현 담당이 가장 단순한 쪽으로 정했고, 리뷰어가 스펙과 대조해 확인했다.

| 정한 것 | 고른 것 | 이유 |
| --- | --- | --- |
| `P01`(모델 id 중복) 문구 | `duplicate model id "<id>" (also in <다른 model.yaml>)`, 위치는 `/id`. 셋 이상이면 첫째는 둘째를, 나머지는 첫째를 가리킨다 | 다른 모델을 전부 나열하면 출력이 모델 수의 제곱으로 커진다. R01과 같은 방식이다 |
| `P02`(모델 안의 모델) 문구 | `model.yaml inside another model (<바깥 model.yaml>)`, 위치는 1:1 | 가리킬 키가 없는 오류라 파일 첫머리를 쓴다(FR-08의 순서) |
| `OK` 줄의 개수 세는 법 | 읽은 항목 수 | `OK` 줄은 오류가 없을 때만 나오고, 그때는 옛 도구의 "고유 id 수"와 값이 같다 |
| 출력 순서 | 프로젝트 오류 먼저, 그다음 모델 순서대로. 함께 쓰는 사전의 오류는 모델마다 한 번 | FR-10의 마지막 항목과 맞는다 |
| 계획 6.2와 스펙이 어긋난 곳 | 스펙을 따랐다. id가 같은 두 모델은 둘 다 `P01`을 받아 `OK` 줄이 없다 | 스펙이 기준이다 |

### D-09. 단계 6A 리뷰(1회차) FAIL 뒤의 처리 (2026-11-28)

- **상황**: 치명 0건, 경고 1건, 참고 6건. 경고는 읽을 수 없는 파일이나 폴더를 만나면 CLI가 스택을 찍고 종료 코드 1로 끝나는 것이다. 종료 코드 1은 "모델에 오류가 있다"는 뜻이라 CI 스크립트가 둘을 구분할 수 없다.
- **선택지(종료 코드)**: (가) 2를 "검사를 실행하지 못함"으로 넓혀 쓴다 (나) 새 코드 3을 만든다
- **고른 것**: (가). 0은 오류 없음, 1은 모델에 오류 있음, 2는 검사를 하지 못함(사용법 오류, 폴더가 아님, 모델 없음, 읽기 실패)이다. stderr에 `Cannot read <dir>: <이유>` 한 줄을 낸다.
- **이유**: 쓰는 쪽에서 필요한 구분은 "모델을 고쳐야 하나, 실행 환경을 고쳐야 하나" 둘뿐이다. 코드를 늘리면 스크립트가 다뤄야 할 경우만 늘어난다.
- **선택지(읽을 수 없는 폴더)**: (가) 검사를 멈춘다 (나) 건너뛰고 계속한다
- **고른 것**: (가). 건너뛰면 그 안에 있던 모델이 검사되지 않은 채 "오류 없음"으로 끝날 수 있다. 검사 도구는 조용히 덜 검사하는 것보다 멈추는 쪽이 안전하다.
- **함께 고치는 참고 사항**: 경로에 줄바꿈 같은 제어 문자가 있으면 출력 한 건이 여러 줄로 갈라져 가짜 줄을 만들 수 있으므로 이스케이프한다. 알 수 없는 명령의 오류를 한 줄로 줄인다. 대조 테스트의 행별 확인을 "오류 줄이 실제로 있는 사례"로 강화한다. 모델 id 시간 테스트에 빨리 실패하는 사전 점검을 넣는다.
- **재리뷰**: 종료 코드와 출력 형식이 바뀌므로 2회차 리뷰를 받는다.
- **타당성**: 리뷰어가 `chmod 000`으로 세 경우를 재현했다. 수정 결과는 아직 확인되지 않았다. 6A 커밋(`3bde0e3`)의 CI는 성공했다(AC-16).
