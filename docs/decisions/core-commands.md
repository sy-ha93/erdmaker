# F03 `core-commands` 진행 중 결정 기록

사용자 지시(2026-11-27, 28)에 따라 선택이 필요한 곳에서는 묻지 않고 권고안대로 진행하고, 그때마다 무엇을 골랐고 왜 타당한지를 여기에 적는다. 기능 끝에 브랜치 전체를 Codex로 한 번 더 리뷰하고, PR을 열어 CI 통과 뒤 직접 스쿼시 병합한다.

각 항목은 선택지, 고른 것, 이유, 타당성(무엇으로 확인했는지 또는 확인하지 못했는지) 순서로 적는다.

## 결정 기록

### D-00. 범위 (2026-11-28)

- **선택지**: (가) 백로그의 F03 범위 그대로 (나) 관계나 사전 명령 일부를 당겨 온다
- **고른 것**: (가)
  - 포함: 명령 API. 엔터티·속성·키(PK, AK, IE)의 생성·수정·삭제·순서 변경, 이름 변경, 주제영역 편집, `scope` 변경, 실행 취소와 다시 실행, 이름에서 ID 만들기(고정, 겹치면 접미사), 명령마다 검증.
  - 제외: 관계 명령(F04), 사전 명령(F05), 화면과 MCP 연결(F09 이후), 저장 시점 정책과 파일 감시(F09~F10).
- **이유**: 백로그가 의존 순서대로 나뉘어 있고, F04와 F05가 모두 F03의 명령 틀 위에 선다. 틀을 먼저 작게 굳히는 편이 뒤 기능의 재작업을 줄인다.
- **F02에서 넘어온 조건**: 명령이 새 항목의 `file` 경로를 만들 때 정규화하면 겹치지 않아야 하고(D-07), "검증 통과 → 저장"이 성립해야 한다(D-06). 같은 객체를 여러 곳에서 공유한 채 넘기지 않는다(D-11).
- **진행 방식에서 바꾼 것**: F02에서 리뷰 한도를 다 쓴 뒤 요구를 바꾼 곳(D-03)에서 마지막 Codex 리뷰가 치명 건을 찾았다. 이번에는 그런 변경이 생기면 그 자리에서 Codex 리뷰를 붙인다. Codex에는 임시 폴더 쓰기 권한을 줘 실제 파일로 확인하게 한다.
- **타당성**: 범위는 백로그 문서(`docs/stage1-backlog.md`)의 F03 항목과 같다. 사용자가 따로 확인한 것은 아니다.

### D-01. 스펙 초안에서 정한 것 (2026-11-28)

스펙 작성 중 정한 설계다. 자세한 내용은 `docs/specs/core-commands.md`에 있다.

| 정한 것 | 고른 것 | 이유 |
| --- | --- | --- |
| 모델 상태 | 불변. 바뀌지 않은 항목은 같은 객체를 그대로 쓴다 | 실행 취소가 단순해지고, 바뀐 파일을 객체 동일성으로 알 수 있다 |
| 실행 취소 | 모델 스냅숏, 100단계, 메모리에만 | 역명령은 명령마다 짝을 만들어야 하고 F04의 전파에서 틀리기 쉽다. 스냅숏은 바뀐 항목만 새로 잡으므로 메모리가 작다 |
| 묶음 명령(`batch`) | 지금 넣는다. 전부 되거나 전부 안 되고, 실행 취소 한 단계다 | F04의 "실행 취소 한 번으로 이주 전체가 되돌아간다"가 이 위에 선다 |
| 한글 이름의 ID | 물리명 우선, 없으면 한글을 고정 표로 로마자화(`고객` → `gogaek`) | 표가 없으면 한글 이름의 객체가 모두 `entity_7` 같은 ID를 받아, 형식 문서의 "읽을 수 있는 ID"와 어긋난다 |
| 이름 변경 | 따로 두지 않고 `*.update`로 한다. `id`와 `file`은 어떤 명령으로도 바뀌지 않는다 | 명령 수가 줄고 "ID는 바뀌지 않는다"가 구조로 보장된다 |
| 참조된 것의 삭제 | F03은 자기가 가진 것만 연쇄로 지운다(주제영역 소속, 배치 노드, 키의 속성). 관계가 가리키는 것은 검증이 거부한다 | 관계 처리는 F04다. 그때까지 관계에 묶인 엔터티는 지울 수 없다(알려진 한계) |

- **타당성**: 스펙 리뷰 전의 결정이다. 실행해 확인한 것은 로마자 변환 예시와 성능 측정값뿐이다.

### D-02. Codex 스펙 리뷰 1회차 REVISE 뒤의 처리 (2026-11-28)

- **상황**: 막는 지적 2건, 주요 10건, 가벼운 3건. 구조(단일 진입점, 스냅숏, 묶음)는 F04가 얹을 수 있다는 평가였다.
- **고른 것**: 전부 반영하고 2회차 리뷰를 받는다. 선택이 갈리는 것은 아래처럼 정했다.

| 지적 | 선택지 | 고른 것과 이유 |
| --- | --- | --- |
| 거부 규칙: "(규칙, 파일, 메시지)별 오류 수가 늘면 거부"가 해로운 편집을 받고 무해한 편집을 거부함 | (가) 명령 뒤 오류가 0이어야 한다 (나) 전체 오류 수가 늘지 않으면 된다 (다) 규칙별로 안정된 위반 식별자를 만든다 | **(나)**. 오류 없는 모델은 항상 오류 없는 채로 남는다. (가)는 Git 병합 등으로 오류가 하나라도 있는 모델을 화면에서 하나씩 고칠 수 없게 만든다. (다)는 규칙 12개마다 식별자를 정의해야 해 이 기능의 크기를 넘는다. 잃는 것: 이미 깨진 모델에서는 오류 하나를 다른 것으로 바꾸는 명령이 통과할 수 있다. 알려진 한계에 예와 함께 적는다 |
| 저장 API: 경로 목록을 받아 "모델에 없는 경로는 지운다"는 모델과 무관한 파일을 지울 수 있음 | (가) 경로 검사를 더한다 (나) 저장 전 모델과 저장할 모델 둘을 받아 차이만 쓴다 | **(나)** `writeChanges(fs, before, after)`. 지우는 것은 `before`가 가졌던 경로뿐이라 구조적으로 남의 파일을 지울 수 없고, 편집 뒤 실행 취소하면 쓸 것이 없어진다. 경로 검사를 덧붙이는 쪽은 F02의 링크 검사처럼 수렴하지 않을 위험이 있다 |
| 외부 편집과의 충돌 감지, 부분 실패 보고 | (가) 지금 (나) F10 | **(나)**. F02 D-11과 같다. 저장 흐름과 파일 감시를 만드는 기능의 일이다 |
| 신뢰할 수 없는 입력 | F02의 값 검사기를 재사용 / 전용 복사기 | **전용 복사기**. 입력을 한도(깊이 32, 값 10만 개, 문자 100만 자) 안에서 평범한 데이터로 복사한 뒤 복사본만 쓴다. F02 검사기는 한도에서 일찍 멈추지 않고, 읽을 때마다 값이 바뀌는 객체를 막지 못한다 |
| "변화 없음"의 정의 | 깊은 비교 / 직렬화한 글 비교 | **직렬화한 글 비교**. 키 순서, `-0`, 기본값 명시 같은 경우가 따로 규칙 없이 정리된다 |
| 성능 요구 | 수치 여러 개 / 회귀 방지용 하나 | **하나**. 측정값은 한 컴퓨터의 관찰이다. "제곱이 없다"를 요구로 두고 수치 관문은 하나만 둔다 |

- **스펙 크기**: F02에서 스펙이 리뷰를 돌 때마다 커졌다. 덧붙이지 말고 바꿔 쓰도록 지시했고, 회차마다 줄 수를 확인한다.
- **타당성**: Codex가 거부 규칙의 반례 세 가지를 코드 위치와 함께 제시했다. 새 규칙에서 세 경우의 기대 결과를 수용 테스트로 넣게 했다. 수정된 스펙은 아직 리뷰받지 않았다.
