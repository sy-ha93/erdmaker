## 요약

목표는 erwin Data Modeler 수준의 논리/물리 모델링을 웹에서 하고, Git으로 버전을 관리하며, 사람과 AI 에이전트가 같은 모델을 함께 고치는 오픈소스 도구다.

- **그대로 쓸 오픈소스는 없다.** 가장 가까운 것은 erd-editor(MIT)로, 단어사전·공동 편집·MCP가 이미 있다. 코드를 검증한 결과 논리 모델을 넣을 구조가 아니어서 포크 대신 새 코어로 만들기로 확정했다(2026-11-26). drawDB와 ChartDB는 AGPL이고 협업·버전관리가 유료다.
- **차별점은 네 가지다.** 진짜 논리 모델(FK 이주, 롤네임, 서브타입), 표준 단어사전, Git 브랜치·PR 기반 협업, 모델·사전·DB를 함께 다루는 MCP.
- **구조의 핵심은 세 가지다.** 모델은 Git에 들어가는 텍스트 파일이고, 모든 편집은 UI·MCP·CLI가 함께 쓰는 코어의 명령 API를 거친다. 그리고 로그인·DB·서버가 없는 설치형이라 협업은 사용자의 Git 클라이언트와 GitHub/GitLab의 브랜치·PR로 한다(2026-11-26 확정).
- **순서**: 2주 준비(erd-editor 검증, 파일 형식 확정) → 약 3개월 MVP(혼자 쓰는 모델러 + MCP) → 약 3개월 팀 기능(병합 화면, PR 자동 검사, DB 연동) → AI 확장.
- **먼저 정할 것**: 제품 이름. 저장소는 github.com/sy-ha93/erdmaker로 분리했다(2026-11-27). 라이선스(Apache-2.0), MVP 범위, 투입(1명)과 첫 공개 목표일(2027-02-26)은 확정했다. 1단계 일정은 기능 백로그(docs/stage1-backlog.md)에 있다. 목록은 7.4에 있다.

## 1. ERwin 개요 문서에서 도출한 필수 기능

`ERwin_Overview.pdf`는 기능 매뉴얼이 아니라 CA ERwin Data Modeler r9.64.01의 *Data Modeling Overview Guide*(98쪽, 8장 + 부록)로, IDEF1X·IE 모델링 방법론을 설명한다. 따라서 필수 기능은 "이 방법론을 도구가 지켜 주려면 무엇이 있어야 하는가"로 도출했다. 그림은 보지 않고 추출한 텍스트만 사용했다.

| 영역 | PDF 근거 (장) | 도구에 꼭 필요한 기능 |
| --- | --- | --- |
| 모델 수준 | 2장 모델링 아키텍처 | 하나의 모델 안에 논리 모델과 물리 모델을 함께 두고 보기 전환. 논리는 ERD → 키 기반(KB) → 완전 속성(FA) 순으로 상세화할 수 있도록 표시 수준(엔터티만 / 키만 / 전체 속성) 제공 |
| 주제영역 | 2장 물리 모델 | 큰 모델을 주제영역(subject area)으로 나눠 따로 그리고, 보고하고, DDL을 생성 |
| 표기법 | 1장, 6장 | IE(까마귀발)와 IDEF1X 표기 전환. 국내 실무 기준으로 IE를 기본값으로 |
| 엔터티·속성 | 3장, 4장 | 엔터티 상자의 키 영역/일반 영역 구분, PK, 대체키(AK), 역엔트리(IE, 비고유 인덱스) 키 그룹 |
| 관계 | 4장, 6장 | 식별(실선)/비식별(점선) 관계, 카디널리티(0·1·N, 정확히 N), 필수/선택, 동사구(verb phrase) |
| FK 자동 이주 | 4장, 7장 | 관계를 그리면 부모 PK가 자식으로 자동 이주. 식별이면 PK 영역, 비식별이면 일반 영역. 종속/독립 엔터티 자동 판정(모서리 모양) |
| 롤네임·단일화 | 5장, 7장 | 같은 부모에서 두 번 이주한 FK에 롤네임 부여. 롤네임이 없으면 자동 단일화(unification) |
| 특수 관계 | 6장 | 다대다(물리에서 연관 테이블로 해소, 원 관계와 연결 유지), 재귀 관계, N항 관계, 서브타입(완전/불완전, 배타/포괄, 구분자 속성) |
| 참조 무결성 | 6장 | 부모·자식 × INSERT·UPDATE·DELETE 6가지 동작별 규칙(Cascade, Restrict, Set Null, Set Default, None)과 다이어그램 표기(D:C 등) |
| 이름·정의 | 5장 | 엔터티·속성 정의(설명, 업무 예시, 코멘트: 담당자·출처·상태), 이름 유일성 검사, 동의어·동음이의어·별칭 관리, 업무 용어집(glossary)과 정의 안의 용어 연결 |
| 도메인·검증 규칙 | 5장, 8장 | 도메인(text, number, datetime, blob 기반 사용자 도메인), 유효값 목록과 의미, 기본값. 물리에서는 CHECK 제약으로 생성 |
| 정규화 지원 | 7장 | 전체 정규화 알고리즘은 ERwin에도 없다. 대신 중복 이름 경고, 롤네임 없는 FK 중복 방지 같은 실시간 검사로 오류를 예방 |
| 논리 → 물리 변환 | 8장 | 엔터티→테이블, 속성→컬럼, 논리 타입→DBMS별 물리 타입, PK/AK/IE→인덱스, 검증 규칙→제약, RI→FK 옵션 또는 트리거 |
| 비정규화 | 8장 | "논리 전용" / "물리 전용" 표시로 한쪽 모델에만 존재하는 객체 허용. 서브타입을 물리에서 통합·분리 |
| 스키마 생성 | 8장 | 선택한 대상 DBMS 문법으로 DDL 스크립트 생성 또는 DB 카탈로그에 직접 적용. 뷰, 사전/사후 스크립트 포함 |

이 문서에 **없는** 것: 리버스 엔지니어링, Complete Compare(모델↔DB 비교), 명명 표준(Naming Standards) 편집기, 리포트, 모델 마트(협업 저장소)는 다루지 않는다. 이들은 사용자가 따로 요청한 요구사항(DB 연동, 단어사전, 협업, 버전관리)으로 3장에서 채운다.

기존 오픈소스 웹 ERD 도구와 가장 크게 갈리는 지점은 세 가지다: 논리/물리 이중 모델, FK 자동 이주와 롤네임·단일화, 서브타입. 이 셋이 "그림 도구"와 "모델링 도구"를 가른다.

### 어느 도구도 채우지 못한 것

- 물리 모델과 분리된 진짜 논리 모델: 서브타입, FK 이주·롤네임, 논리 하나에 물리 여럿.
- 모델 ↔ 실제 DB 비교와 마이그레이션 스크립트.
- 계정·권한·브랜치·리뷰가 있는 서버형 협업을 오픈소스로 제공하는 것. drawDB와 ChartDB는 이 부분이 유료다.
- 모델, 사전, 실제 DB를 한 번에 다루는 MCP 서버.
- 여러 모델이 공유하는 표준 사전과 준수 보고서.

### 권고: 새 코어로 만들고, erd-editor와는 파일·사전을 호환시킨다

- **drawDB, ChartDB 포크는 권하지 않는다.** AGPL이라 파생물도 AGPL이 되고, 핵심 차별점(논리 모델, 사전)이 데이터 구조에 없다.
- **erd-editor는 출발점 후보다.** MIT이고 사전·MCP·Yjs가 이미 있다. 다만 논리 모델을 별도 계층으로 넣으려면 데이터 구조를 바꿔야 한다. 코드를 읽어 본 결과는 아래 검증 결과에 있다.
- **기본 방침은 새 코어 + 검증된 라이브러리 조합**이다. 코어는 직접 만들고, 캔버스·CRDT·파서·diff는 5.3의 라이브러리를 쓴다. `.erd.json`과 DBML 가져오기를 넣어 기존 사용자가 옮겨 올 수 있게 한다.

### erd-editor 검증 결과 (2026-11-26)

결론은 포크도 기여도 아닌 **새 코어**다. erd-editor는 호환 대상이자 설계 참고로 쓴다. 저장소(커밋 dff83b0, 2026-11-03)를 읽고 npm 패키지 5.1.0을 Node 22에서 실행해 확인했다.

| 확인한 것 | 결과 | 우리에게 뜻하는 것 |
| --- | --- | --- |
| 데이터 구조 (스키마 v3) | 테이블·컬럼에 `name`과 `logicalName`이 함께 있는 물리 모델 하나. 관계에 식별 여부, 카디널리티, ON DELETE/UPDATE는 있다 | 논리 모델이 별도 계층이 아니다 |
| 스키마에 없는 개념 | 서브타입, 롤네임, 주제영역(다이어그램 여럿), 논리 전용/물리 전용, 다대다, 대체키 그룹. 묶음은 테이블 그룹뿐 | 1장 필수 기능의 절반이 스키마 변경을 요구한다 |
| 파일 형식 | `.erd.json` 파일 하나. ID 키로 정렬되어 안정적이지만 좌표와 너비가 테이블·관계 레코드 안에 섞여 있다 | 배치만 바꿔도 모델 diff가 생긴다. 엔터티별 파일 분리도 아니다 |
| 화면 없는 실행 | `peer.js`로 Node에서 문서 로드, 저장 형식 왕복(바이트 동일), PostgreSQL DDL 생성까지 동작. 다만 글자 너비 함수를 넘겨야 로드된다 | 엔진이 레이아웃 계산과 묶여 있다. 변환 도구로 쓰기에는 충분하다 |
| 코드 규모와 기반 | `erd-editor` 패키지만 TypeScript 약 47만 줄(테스트가 절반 이상), 21개 패키지. UI는 자체 프레임워크(r-html) + Konva | 포크하면 이 전부를 유지해야 한다. React 생태계를 쓸 수 없다 |
| 유지 체계 | 커밋 1,868건이 한 사람, 최근 병합 PR도 모두 본인. VS Code·IntelliJ·Obsidian 플러그인을 함께 배포 | 스키마를 바꾸는 기여는 5개 배포처에 파급된다. 받아들여질 가능성이 낮다 |
| MCP | 도구 60개 이상. 엔진의 액션 목록에서 도구를 만들고, 일치 여부를 테스트로 강제한다 | 4장의 "UI와 MCP가 같은 명령 API" 설계가 실제로 통한다는 근거 |
| 사전 | 단어(약어, 영문명, 동의어, 금칙어), 용어(물리명, 도메인), 도메인(분류, 타입). 물리명 자동 유도와 검사 도구 포함 | 3.2의 필드 구성을 이와 맞춰 두면 사전을 서로 옮길 수 있다 |

가져갈 것은 세 가지다.

- **호환**: `.erd.json` 가져오기와 내보내기를 MVP에 넣는다. 공개된 JSON Schema가 있어 변환기를 쓰기 쉽다.
- **사전 필드**: 단어·용어·도메인의 필드를 erd-editor와 호환되게 잡는다.
- **설계 방식**: 액션 목록에서 MCP 도구를 생성하고, 도구와 액션의 일치를 테스트로 검사한다.

확인하지 않은 것: 브라우저에서의 편집 사용감, 테이블 수백 개에서의 캔버스 성능, Yjs 공동 편집의 실제 동작.

## 3. 상위 요구사항

요구사항은 8개 영역, 단계는 MVP → 2단계 → 3단계로 나눈다. 단계별 일정은 7장에 있다.

### 3.1 모델링 코어 (MVP)

1장 표의 기능 전체가 대상이다. MVP에서는 IE 표기, 논리/물리 전환, 식별·비식별 관계와 FK 자동 이주, 롤네임, 주제영역, 도메인, 실시간 검증까지 넣는다. IDEF1X 표기, N항 관계, RI 6동작 트리거 생성은 2단계로 미룬다. 서브타입은 MVP에 표기만 넣고, 물리 변환 옵션(통합·분리)은 2단계에 넣는다.

### 3.2 단어사전과 표준화 (MVP 일부, 2단계 완성)

국내 공공·금융 데이터 표준 관행(표준단어 → 표준용어 → 표준도메인)을 그대로 따른다.

- **표준단어**: 한글명, 영문명, 영문약어, 정의, 분류어 여부(예: 번호, 금액, 일자), 동의어·금칙어.
- **표준용어**: 단어의 조합. 한글 용어를 입력하면 단어를 분해해 물리 컬럼명을 자동 생성한다(고객번호 → CUST\_NO).
- **표준도메인**: 분류어에 묶인 논리 타입과 길이, DBMS별 물리 타입 매핑, 유효값 목록.
- **준수 검사**: 사전에 없는 단어, 약어 불일치, 도메인 불일치를 캔버스와 목록에서 경고하고 준수율을 보여 준다.
- **가져오기**: 공공데이터 공통표준용어(행정안전부 배포 엑셀)와 사내 표준 엑셀을 그대로 가져온다.
- 사전은 모델과 분리된 파일로 두어 여러 모델이 공유한다.

### 3.3 Import / Export (MVP 일부)

| 방향 | 형식 | 단계 |
| --- | --- | --- |
| 가져오기 | SQL DDL (MySQL, PostgreSQL) | MVP |
| 가져오기 | DBML, 엑셀(테이블 정의서·컬럼 정의서) | MVP |
| 가져오기 | erwin XML, ERDCloud·DA#·eXERD 내보내기 파일, Mermaid erDiagram, Prisma schema | 2단계 (형식별 가능 여부 조사 필요) |
| 내보내기 | SQL DDL, DBML, Mermaid, PNG/SVG/PDF | MVP |
| 내보내기 | 엑셀 산출물: 테이블 정의서, 컬럼 정의서, 엔터티 정의서, 용어사전 (서식 템플릿 교체 가능) | MVP |
| 내보내기 | 정적 HTML 뷰어 (서버 없이 열리는 단일 파일) | MVP |
| 내보내기 | ORM 스키마 (Prisma, TypeORM, JPA 엔터티, SQLAlchemy, Drizzle), JSON Schema, 마이그레이션 파일 (Flyway, Liquibase) | 2단계 |

### 3.4 실제 DB 연동 (2단계)

- **리버스 엔지니어링**: 카탈로그(information\_schema 등)에서 테이블, 컬럼, 주석, PK/FK/인덱스, 뷰를 읽어 물리 모델을 만든다. 주석은 논리명 후보로 쓴다.
- **포워드 엔지니어링**: 전체 DDL 생성, 또는 모델과 DB의 차이만 ALTER 스크립트로 생성.
- **비교(Complete Compare)**: 모델 ↔ DB, 모델 ↔ 모델을 객체 단위로 비교하고 방향을 골라 병합.
- **FK 추정**: FK 제약이 없는 레거시 DB는 컬럼명·타입 일치와 고아 행 검사 쿼리로 관계 후보를 제안하고 사람이 승인한다. 사내 분석 프로젝트에서 쓴 "상·중·하 근거 등급 + 승인" 방식을 제품 기능으로 옮긴다.
- **대상 DBMS**: 기본은 MySQL/MariaDB와 PostgreSQL. 다음 순서로 Oracle, SQL Server, SQLite를 제안한다(국내 SI 수요 순). 그 뒤 Tibero, CUBRID, 분석용(BigQuery, Snowflake, ClickHouse)은 방언 플러그인으로 연다.
- **접속 방식**: 브라우저는 DB에 직접 붙을 수 없으므로 로컬 프로그램(CLI)이 접속해 스키마를 읽는다. DB 비밀번호는 모델 폴더에 저장하지 않는다. 운영 DB에는 읽기 전용 계정을 권장하고, DDL 직접 실행은 기본 꺼짐으로 둔다.

### 3.5 공유와 협업 (2단계)

- **협업은 Git으로 한다.** 사람마다 브랜치에서 작업하고 PR(GitLab은 MR)로 합친다. 권한, 리뷰, 이력은 GitHub/GitLab이 맡는다(3.6).
- **프로그램에는 로그인, 계정, 역할이 없다.** 편집 권한은 저장소 권한이다.
- **댓글과 검토는 PR에서 한다.** PR에 변경 요약과 ERD 이미지가 달려, 프로그램을 설치하지 않은 사람도 검토한다.
- **보기 전용 공유**는 단일 파일 HTML 뷰어(3.3)를 내보내 GitHub Pages 같은 정적 호스팅에 올린다.
- 네트워크 없이 편집된다. 원본이 로컬 파일이기 때문이다.
- **넣지 않는 것**(2026-11-26 확정): 실시간 공동 편집, 다른 사람의 커서 표시, 공유 링크와 역할 관리, 동기화 서버. 수요가 확인되면 다시 본다.

### 3.6 버전관리와 Git (MVP 일부, 2단계 완성)

- **모델은 텍스트 파일이다.** 엔터티 하나가 파일 하나인 YAML/JSON으로 저장해 `git diff`와 PR 리뷰가 읽힌다. 좌표 같은 레이아웃 정보는 별도 파일로 분리해 의미 없는 diff를 막는다.
- **앱은 Git을 조작하지 않는다**(2026-11-26 확정). 브랜치, 커밋, 푸시, PR은 사용자가 쓰던 Git 클라이언트(명령줄, GitHub Desktop, VS Code 등)나 코딩 에이전트로 한다. 앱은 폴더의 파일을 고치고, 밖에서 바뀌면 다시 읽는다. 인증을 다루지 않으므로 GitHub과 GitLab을 가리지 않는다.
- **모델 diff** (MVP): 기준 버전(예: `main`)과 비교해 "엔터티 2개 추가, 컬럼 타입 1건 변경"처럼 의미 단위로 보여 주고, 캔버스에 추가·변경·삭제를 색으로 표시한다. Git에서는 읽기만 한다.
- **3-way 병합** (2단계): 같은 속성을 양쪽에서 고쳤을 때만 충돌로 묻는 병합 화면이다. `git mergetool`과 `git difftool`에 등록해 어떤 Git 클라이언트에서도 뜬다. 배치 파일은 한쪽을 택하는 규칙으로 합친다.
- **PR 자동화** (2단계): PR이 열리면 검증 결과, 변경 요약, ERD 이미지, 마이그레이션 SQL 초안, 표준 준수 검사 결과를 댓글로 단다. GitHub Action과 GitLab CI로 제공한다. GitHub과 GitLab.com의 병합 버튼은 모델 단위 병합을 실행하지 않으므로, 충돌 없이 합쳐진 결과가 깨졌는지는 이 검사가 막는다.
- 태그로 버전(베이스라인)을 찍고, 두 버전 사이의 ALTER 스크립트를 뽑는다.
- VS Code 확장은 수요를 보고 검토한다.

### 3.7 저장과 실행 방식 (MVP)

- **설치형이다**(2026-11-26 확정). `npx erdmaker serve <모델 폴더>`가 로컬 프로그램을 띄우고 브라우저에서 편집기를 연다. 로그인, DB, 서버가 없다.
- 편집 내용은 모델 폴더의 파일에 즉시 쓴다. 저장 버튼이 없고 새로고침해도 남는다.
- 파일이 밖에서 바뀌면(MCP, 코딩 에이전트, `git pull`) 화면이 다시 읽는다. UI, MCP, CLI, Git이 같은 파일을 본다.
- **넣지 않는 것**: 브라우저 안의 SQLite 저장, 설치 없는 정적 웹 편집기, `docker compose` 자체 호스팅, 클라우드 호스팅. 설치 없이 보는 용도는 단일 파일 HTML 뷰어(3.3)가 맡는다.

### 3.8 추가로 권하는 기능

- **모델 린트**: PK 없는 테이블, 인덱스 없는 FK, 예약어 사용, 정의 누락, 순환 참조를 규칙으로 검사. 규칙은 설정 파일로 켜고 끈다.
- **영향도 분석**: 컬럼을 바꾸면 영향받는 FK, 뷰, 인덱스를 보여 준다.
- **대형 모델 대응**: 테이블 1,000개에서도 버벅이지 않는 캔버스, 검색, 미니맵, 자동 배치, 주제영역별 배치 저장.
- **샘플 데이터 생성**: 도메인과 유효값을 이용한 테스트 INSERT 생성.
- **데이터 리니지·코드 연결**(3단계): 테이블을 쓰는 화면·쿼리 연결. 사내 분석 프로젝트의 추적 탐색기와 같은 방향이다.

## 4. AI 기능: 에이전트, MCP, 자연어 모델링

AI 기능의 전제는 하나다: 사람이 UI로 하는 모든 편집을 같은 명령(command) API로 노출하고, UI·MCP·CLI가 그 API를 함께 쓴다. 그러면 에이전트가 한 일도 실행 취소, 검증, diff, 협업 동기화를 그대로 탄다.

### 4.1 MCP 서버 (MVP)

제품이 MCP 서버를 제공해 Claude Code, Cursor 같은 외부 에이전트가 모델을 읽고 고친다. stdio로 붙는다.

| 분류 | 도구 예시 |
| --- | --- |
| 읽기 | `list_entities`, `get_entity`, `search_model`, `get_subject_area`, `lookup_term` |
| 편집 | `create_entity`, `add_attribute`, `create_relationship`, `rename`, `apply_changeset` |
| 검증 | `validate_model`, `check_naming`, `lint` |
| 생성 | `generate_ddl`, `generate_migration`, `export` (DBML, Mermaid, 이미지) |
| DB | `introspect_database`, `compare_with_database` |
| 버전 | `diff` |

- 편집 도구는 바로 반영하지 않고 **변경안(changeset)** 을 만든다. 사람이 캔버스에서 diff를 보고 수락하거나 거절한다. 자동 적용은 설정으로 켠다.
- 모델이 텍스트 파일이므로 MCP 없이도 코딩 에이전트가 파일을 직접 고칠 수 있다. 이때는 CLI의 `validate`가 안전망이다.

### 4.2 내장 에이전트 (2단계)

- 우측 패널의 대화창. 선택한 엔터티·주제영역을 문맥으로 넘기고, 제안은 변경안으로 돌아온다.
- LLM 제공자는 교체 가능하게 둔다(사용자 API 키, 사내 게이트웨이, 로컬 모델). 키는 사용자의 컴퓨터에만 둔다.
- 보내는 것은 스키마 메타데이터뿐이고 실제 데이터 행은 보내지 않는다.

에이전트가 할 일: 정의 초안 작성, 한글 논리명 → 표준용어 매핑과 신규 단어 제안, 정규화 검토(반복 그룹, 파생 속성, 중복 사실 지적), 레거시 DB의 FK 추정, 주석 없는 컬럼의 논리명 추정, 인덱스 제안, 마이그레이션 위험 설명, PR 리뷰.

### 4.3 자연어 → 업무프로세스 → 모델 → SQL (3단계)

한 번에 SQL까지 가지 않고, 단계마다 산출물을 남기고 사람이 확인한다. 각 산출물은 저장소에 파일로 남아 추적된다.

1. **요구 입력**: 업무 설명, 회의록, 화면 설계서, 기존 엑셀 양식을 붙여 넣는다.
2. **업무 프로세스 정리**: 행위자, 단계, 업무 규칙, 다루는 정보를 뽑아 프로세스 흐름도와 규칙 목록으로 보여 준다. 사람이 고친다.
3. **개념 모델**: 명사에서 엔터티 후보, 동사에서 관계 후보를 만든다. 각 후보에 근거 문장을 붙인다.
4. **논리 모델**: 키, 속성, 카디널리티, 서브타입을 채우고 단어사전으로 이름을 표준화한다. 검증기가 규칙 위반을 잡는다.
5. **물리 모델**: 대상 DBMS를 고르면 타입 매핑, 인덱스, 비정규화 제안을 받는다.
6. **SQL**: DDL과 마이그레이션을 생성한다. 이 단계는 LLM이 아니라 결정적 생성기가 만든다.
7. **검증**: 임시 DB(브라우저 안의 PGlite 또는 컨테이너)에 적용해 보고, 업무 시나리오에서 나온 질의가 실행되는지 확인한다.

핵심 원칙은 LLM이 구조를 제안하고, 규칙 기반 엔진이 검증과 SQL 생성을 맡는 분업이다. 같은 모델에서는 항상 같은 SQL이 나온다.

### 4.4 Vanna식 자연어 질의 (3단계)

Vanna는 스키마, 문서, 질문-SQL 예시를 검색해 LLM에 넘겨 SQL을 만드는 text-to-SQL 도구다(MIT). 다만 GitHub 저장소가 2026-03-29에 보관(archived) 처리되어 마지막 릴리스는 v2.0.2다. 의존하지 말고 방식만 빌린다. 이 제품은 그 검색 재료를 이미 갖고 있다는 점이 강점이다.

- **모델이 곧 문맥**: 논리명, 정의, 유효값 의미, 관계, 용어사전을 text-to-SQL의 검색 대상으로 내보낸다. 컬럼명만 있는 DDL보다 정확도가 올라간다.
- **질의로 모델 검증**: "월별 환불 금액을 상품별로" 같은 업무 질문을 설계 단계에서 던져, 모델이 답할 수 있는지 본다. 답이 안 나오면 빠진 엔터티나 속성이 있다는 뜻이다.
- **연동 방식**: 특정 도구를 내장하지 않고 검색용 내보내기(DDL + 문서 + 예시 질의)와 MCP로 연결한다. 실제 DB 질의는 DBHub 같은 기존 DB MCP 서버와 함께 쓰게 한다. 수요가 확인되면 질의 패널을 넣는다.

### 4.5 그 밖의 아이디어

- 화이트보드 사진이나 기존 ERD 이미지를 올리면 모델로 변환.
- 애플리케이션 코드(ORM 엔터티, SQL 매퍼)에서 모델과 관계 근거를 추출. 사내 분석 프로젝트에서 수작업 스크립트로 한 일이다.
- 모델 변경을 주 단위로 요약해 팀에 알리는 변경 노트 자동 작성.
- 에이전트용 스킬 묶음 배포: "레거시 DB 분석", "표준화 점검", "마이그레이션 리뷰" 같은 절차를 프롬프트와 함께 제공.

## 5. 아키텍처와 기술 스택

모델을 다루는 로직은 화면과 분리된 코어 패키지 하나에 모으고, 웹 편집기·MCP 서버·CLI가 그것을 가져다 쓴다.

위 세 클라이언트는 모두 모델 코어의 명령 API를 호출한다. 편집 결과는 모델 폴더의 텍스트 파일에 바로 쓰이고, 그 폴더가 곧 Git 저장소다. 브라우저 저장소와 동기화 서버는 2026-11-26 결정으로 두지 않는다(3.7, 5.2).

### 5.1 모델 파일 형식

형식 v0 초안(formatVersion 0.1)을 2026-11-26에 썼다. 모델은 YAML, 배치는 JSON으로 나누고, 엔터티·관계·서브타입 묶음을 각각 파일 하나로 둔다. 작업 폴더에서 형식 문서는 `docs/format-v0.md`, 스키마 8개와 예제 모델은 `format/v0/`, 검증 스크립트는 `tools/validate-format.mjs`에 있다.

```
<모델 디렉터리>/
  model.yaml                 # 형식 버전, 표기법, 대상 DBMS, 사전 경로
  entities/<id>.yaml         # 엔터티 1개 = 파일 1개 (속성, 키 그룹 포함)
  relationships/<id>.yaml    # 식별, 비식별, 다대다 관계
  subtypes/<id>.yaml         # 서브타입 묶음
  subject-areas/<id>.yaml    # 주제영역과 소속 엔터티
  layouts/<주제영역 id>.json  # 좌표, 꺾임점, 표시 수준
  dictionary/*.yaml          # 단어, 용어, 도메인
```

```yaml
# entities/order.yaml (일부)
id: order
name: 주문
physical:
  name: ORDERS
attributes:
  - id: ord_no
    name: 주문번호
    term: ord_no
    domain: number
    nullable: false
    physical:
      name: ORD_NO
  - id: ship_addr_no
    name: 배송주소번호
    domain: number
    nullable: false
    physical:
      name: SHIP_ADDR_NO
    migratedFrom:
      - relationship: order_ships_to
        attribute: addr_no
    rolenamed: true
keys:
  - id: pk
    kind: primary
    attributes:
      - ord_no
```

| 결정 | 이유 |
| --- | --- |
| 좌표는 `layouts/`에만 둔다 | 상자를 옮겨도 모델 diff가 생기지 않는다 |
| 객체 하나에 파일 하나 | 서로 다른 엔터티를 고치면 Git이 충돌 없이 합친다 |
| ID는 처음 이름에서 만들고 바꾸지 않는다 | 이름 변경이 "삭제 후 추가"가 되지 않고, `parent: customer`처럼 참조가 읽힌다. 이름을 바꾸면 ID와 달라질 수 있다 |
| 이주된 FK 속성을 자식 파일에 이름·타입까지 적는다 | 엔터티 파일만 보고 컬럼 전체를 안다. 부모와 어긋나면 검증기가 잡는다 |
| `name`이 논리명, `physical.name`이 물리명, `scope`로 한쪽 전용 표시 | 논리 속성과 물리 컬럼의 대응을 따로 관리하지 않는다 |
| 타입은 논리 타입이나 도메인, DBMS별 타입은 필요할 때만 덮어쓴다 | 대상 DBMS를 바꿔도 모델이 그대로다 |
| YAML 1.2 코어 스키마만, 앵커·태그 금지 | 번호의 약어 `NO`가 불리언으로 읽히는 문제를 막는다 |
| 사전 필드는 erd-editor의 단어·용어·도메인과 대응 | 사전을 서로 옮길 수 있다 |

검증 스크립트는 스키마 검사 뒤에 파일 간 규칙 9가지를 본다. 예: 부모 키의 각 속성이 자식 속성 정확히 하나로 이주하는지, 재귀 관계에 롤네임이 있는지. 엔터티 10개, 관계 11개짜리 예제가 통과하고, 일부러 망가뜨린 9가지는 모두 오류로 잡혔다.

v0에 넣지 않은 것: N항 관계, 서브타입의 물리 통합·분리 옵션, 뷰·트리거, 추정 관계 후보, 댓글, 논리 하나에 물리 여럿. 모두 키를 추가하는 방식으로 넣을 수 있다.

확인하지 않은 것: 표준용어 수만 건짜리 사전의 로드 시간과 diff 크기, 실제 `.erd.json`의 변환. ID 방식은 이름 기반 고정 ID로 확정했다(2026-11-26).

형식은 JSON Schema(2020-12)로 공개하고 버전을 매긴다. 1.0 전까지는 호환을 깨는 변경마다 `formatVersion`을 올리고 변환 명령을 함께 낸다. 이 형식이 프로젝트의 가장 오래 가는 결정이므로 MVP 전에 먼저 확정한다.

### 5.2 저장과 동기화

- **원본은 모델 폴더의 파일이다.** 편집 명령마다 바뀐 파일만 다시 쓴다. 별도의 DB나 편집 중 상태 저장소가 없다.
- **화면과의 동기화는 파일 감시다.** 로컬 프로그램이 폴더를 감시해 밖에서 바뀐 파일을 화면에 반영한다. 화면에서 고치는 중인 객체가 밖에서도 바뀌면 덮어쓰지 않고 사용자에게 묻는다.
- **사람 사이의 동기화는 Git이다.** 브랜치 간 병합은 모델 단위 3-way 병합으로 한다(3.6).
- **두지 않는 것**: CRDT, 동기화 서버, 서버 DB, 브라우저 SQLite.
- 검색과 영향도 분석은 메모리에 올린 모델에서 처리한다. 테이블 1,000개 규모에서 충분한지는 확인하지 않았다.

### 5.3 기술 스택

허용적 라이선스(MIT, Apache-2.0)로 배포할 수 있는 것만 골랐다. 라이선스는 2026-11-25 각 저장소 기준이다.

| 영역 | 선택 | 라이선스 | 이유와 주의점 |
| --- | --- | --- | --- |
| 언어 | TypeScript 모노레포 |  | 코어를 브라우저·Node·CLI에서 같이 쓴다 |
| 캔버스 | [React Flow (xyflow)](https://github.com/xyflow/xyflow) | MIT | 노드를 React 컴포넌트로 그린다. ChartDB와 Liam이 쓴다. tldraw는 상용 라이선스라 제외 |
| 자동 배치 | [elkjs](https://github.com/kieler/elkjs) | EPL-2.0 | 참고 화면이 이미 ELK를 쓴다. 약한 카피레프트라 수정 없이 의존성으로만 쓴다. 대안은 dagre(MIT) |
| 서버 | Node (HTTP + WebSocket), 파일 감시 |  | serve 명령. 모델 폴더를 읽고 쓰며 파일 변경을 화면에 알린다. DB 없음 |
| SQL 파서 | [node-sql-parser](https://github.com/taozhi8833998/node-sql-parser) | Apache-2.0 | 방언별 브라우저 빌드. drawDB와 ChartDB가 쓴다. sql-parser-cst는 GPL-2.0이라 제외 |
| DBML | [@dbml/core](https://github.com/holistics/dbml) | Apache-2.0 | DBML ↔ SQL 변환 |
| 스키마 diff | 자체 모델 diff + [sqldef](https://github.com/sqldef/sqldef) 검토 | MIT | 모델 간 diff는 코어가 한다. DB 대상 ALTER 생성에 sqldef(MySQL, PostgreSQL, SQLite, MSSQL)를 검토. [Atlas](https://atlasgo.io/community-edition)는 커뮤니티판에 Oracle·MSSQL 드라이버와 뷰·트리거가 빠져 있어 기본 엔진으로 쓰지 않는다 |
| Git | 시스템의 git (읽기만) | MIT | 기준 버전의 파일을 읽어 모델 diff에 쓴다. 쓰기와 인증은 사용자의 Git 클라이언트가 한다. mergetool·difftool로 등록 |
| MCP | 공식 TypeScript SDK | MIT | stdio. SDK 라이선스는 채택 전에 재확인 |
| DB 접속 | CLI 에이전트 (mysql2, pg) | MIT | 카탈로그 조회 쿼리를 방언 플러그인으로 분리 |

MCP SDK, mysql2, pg의 라이선스는 이번 조사에서 저장소를 열어 확인하지 않았다. 채택 전에 확인한다.

## 6. UI 방향

화면은 사내 분석 프로젝트의 ERD 화면 두 개(ERD 탐색기, IE 표기 뷰어)를 합친 모양으로 한다. 탐색기의 3단 배치와 뷰어의 캔버스 조작을 확인했다.

| 영역 | 참고 화면에서 가져올 것 | 편집기로 만들며 더할 것 |
| --- | --- | --- |
| 상단 바 (56px) | 모델 선택, 논리명/물리명 전환, 검색, 화면 맞춤, 자동 배치 | 현재 브랜치 표시(읽기 전용), 기준 버전과 비교, 표기법(IE/IDEF1X) 전환 |
| 왼쪽 패널 (300px) | 업무영역 목록과 테이블 수, 테이블·컬럼·한글명 통합 검색 | 주제영역 트리 편집, 엔터티 목록, 단어사전 탭, 변경 내역 탭 |
| 가운데 캔버스 | 식별 실선 / 비식별 점선, 드래그 이동, 휠 확대, "키 컬럼만" 보기, 다른 영역 테이블은 회색 점선 상자, 범례 | 관계선 끌어서 생성, 인라인 속성 편집, 미니맵, 정렬 안내선, diff 색 표시 |
| 오른쪽 패널 (420px, 너비 조절) | 컬럼 사전 표(키, 컬럼, 한글명·설명, 타입), 확정 관계와 추정 관계 구분, 근거 표시 | 속성 편집 폼, 검증 경고, AI 대화 탭 |

그대로 이어갈 설계 결정:

- **이름 우선순위**: 직접 수정 > DDL 주석 > 추정 후보. 출처를 값마다 기록한다.
- **추정 관계는 기본 숨김**: 근거 등급(상·중·하)을 표시하고 승인한 것만 모델에 넣는다.
- **URL이 공유 단위**: `#모델/area/영역`, `#모델/table/테이블` 주소로 특정 엔터티를 바로 가리킨다.
- **레이아웃은 모델과 분리된 파일**(`layout.json`)로 저장한다.
- 색과 글꼴: 밝은 배경(#f6f8fb), 강조색 파랑(#3868e9), Pretendard. 다크 테마를 추가한다.

바꿀 것: 탐색기는 Cytoscape + ELK로 노드를 한 덩어리 라벨로 그린다. 편집기는 엔터티 상자 안의 속성 행을 직접 다뤄야 하므로 노드를 컴포넌트로 그리는 캔버스 라이브러리로 바꾸고, 자동 배치에만 ELK를 계속 쓴다.

모델 파일 형식과 코어를 먼저 만들고, 혼자 쓰는 모델러를 공개한 뒤 팀 기능과 AI를 얹는다.

1단계는 1명, 13주(2026-11-30 \~ 2027-02-26)로 확정했고 기능별 일정은 docs/stage1-backlog.md에 있다. 2단계 이후의 기간은 추정이다. 2단계에 있던 실시간 공동 편집은 2026-11-26 결정으로 빠졌고, 그 자리는 병합 화면과 PR 자동 검사가 맡는다.

### 7.1 단계별 완료 기준

- **0단계**: erd-editor 코드를 읽고 포크·기여·새 코어 중 하나로 결정한다. 모델 파일 형식 v0을 JSON Schema로 쓴다. 테이블 1,000개 모델로 캔버스 성능을 재본다.
- **1단계 (MVP)**: 실제 운영 규모의 스키마(테이블 363개)를 DDL로 가져와 논리명을 붙이고, 고쳐서, DDL과 엑셀 정의서로 다시 내보낼 수 있다. 외부 에이전트가 MCP로 엔터티를 추가하고 검증을 통과한다.
- **2단계**: 두 사람이 각자 브랜치에서 작업하고 PR로 합친다. 같은 엔터티를 둘이 고친 충돌은 병합 화면에서 푼다. PR에 검증 결과, 모델 diff, ALTER 초안이 달린다. 운영 MySQL과 모델의 차이를 보고서로 본다.
- **3단계**: 업무 설명 한 페이지에서 검토 가능한 논리 모델 초안과 DDL이 나온다.

### 7.2 오픈소스 운영

- **라이선스**: Apache-2.0으로 확정했다(2026-11-26). 특허 조항이 있어 기업이 도입하기 쉽고, MIT·Apache 라이브러리와 충돌이 없다. 클라우드 사업자의 무임승차를 막는 AGPL-3.0은 대안으로 검토했으나 택하지 않았다.
- **유료 전용 기능을 두지 않는다.** drawDB와 ChartDB가 협업·버전관리를 유료로 묶은 자리가 이 프로젝트의 차별점이다. 수익이 필요하면 지원으로 잡는다.
- **공개 시점**: 0단계부터 공개 저장소에서 개발한다. 파일 형식 문서와 예제 모델을 먼저 올린다.
- **문서와 언어**: 한국어와 영어를 함께 둔다. 단어사전과 엑셀 산출물은 국내 수요가 분명한 진입점이다.
- **확장 지점**: DBMS 방언, 가져오기/내보내기 형식, 린트 규칙, 엑셀 템플릿을 플러그인으로 열어 외부 기여를 받는다.
